# 数据治理：数据研发从“能用数据”到“可信数据”的核心能力

> [!abstract] 一句话总结
> 数据开发解决“**有没有数据**”，数据治理解决“**数据能不能信**”。
> 面试中，数据治理是区分“会写 SQL 的人”和“能负责一条数据链路的人”的分水岭。

## 〇、先建立一个统一心智模型

很多人讲数据治理会越讲越散，是因为没有一根主线。本文用一条主线贯穿全文——

> [!important] 主线
> **数据治理 = 让数据持续做到“六可”：可信、可懂、可找、可用、可控、可负担。**

每一项能力，对应一个治理模块，也对应数据研发的一类日常工作：

| 能力（要什么） | 对应模块（做什么） | 数据研发的日常体现 |
| --- | --- | --- |
| 可信 | 数据质量治理 ⭐ | 校验规则、对账、波动监控 |
| 可懂 | 数据标准 + 元数据 | 命名规范、口径文档、血缘 |
| 可找 | 数据资产治理 | 数据地图、资产分级、清理 |
| 可用 | 数仓分层 + 指标统一 | 公共层建设、口径收口 |
| 可控 | 数据安全 + 生命周期 | 权限、脱敏、分级、合规 |
| 可负担 | 成本治理 | 存储/计算/调度优化 |

## 一、什么是数据治理

数据治理是围绕**数据质量、标准、安全、资产、成本和使用效率**建立的一套**长期管理机制**（注意：是机制，不是一次性项目）。

对数据研发来说，它**不是纯管理概念，而是和日常开发强相关**的工程实践。换个说法，下面这些你每天都在做的事，本质都是治理：

- 表/字段命名是否规范，口径是否一致 → **可懂**
- 任务是否稳定、数据是否及时、指标是否准确 → **可信**
- 血缘是否清晰、下游是否知道数据变更 → **可懂 + 可控**
- 权限是否合理、敏感字段是否脱敏 → **可控**
- 存储和计算是否浪费 → **可负担**

> [!tip] 方法论参考
> 业界最权威的框架是 **DAMA-DMBOK**（数据管理知识体系），它以“数据治理”为核心，环绕数据质量、元数据、数据安全、数据架构、主数据等多个职能域。面试时点到 DAMA，能体现你有体系化认知，但**别只背名词**——要能把它和上面的“六可”对应起来讲。

## 二、数据治理的核心内容

> [!note]
> 下面六大模块是数据治理的主干，分别支撑“六可”中的一项或多项。**数据质量和数据标准是面试最高频的两块**。

| 模块     | 支撑的能力 | 解决的核心问题 | 面试重要度 |
| ------ | ----- | ------- | ----- |
| 数据质量治理 | 可信    | 数据准不准   | ⭐⭐⭐⭐⭐ |
| 数据标准治理 | 可懂    | 定义一致    | ⭐⭐⭐   |
| 元数据治理  | 可懂    | 可理解、可追踪 | ⭐⭐⭐   |
| 数据资产治理 | 可找    | 找得到、用得好 | ⭐⭐    |
| 数据安全治理 | 可控    | 用得安全、合规 | ⭐⭐⭐   |
| 成本治理   | 可负担   | 用得起     | ⭐⭐⭐   |

### 1. 数据质量治理 ⭐ 

> [!important] 面试最高频
> 这是面试**最高频**的部分，几乎每场必问。务必能背出六个维度、各举一例，并能说出“怎么监控、怎么告警、怎么闭环”。

数据质量解决“**可信**”的问题。判断质量好坏，业界统一用**六大维度**——记忆口诀：**“完准一时，唯效”**（完整、准确、一致、及时、唯一、有效）。

| 维度  | 含义         | 典型检查             | 例子 |
| --- | ---------- | ---------------- | --- |
| 完整性 | 数据是否缺失     | 字段非空、分区不为空、记录数达标 | 订单表里 `order_id` 为空，或昨天分区 `dt=2026-06-27` 没有数据 |
| 准确性 | 计算是否正确     | 与源系统对账、GMV 复算    | 源系统订单支付金额是 99 元，数仓里算成 109 元 |
| 一致性 | 不同链路结果是否一致 | 实时与离线对比、同指标多表对齐  | 实时报表昨日 GMV 是 100 万，离线报表昨日 GMV 是 95 万 |
| 及时性 | 是否按时产出     | 任务 SLA、产出时间监控    | 每天 8 点前应该产出销售日报，但今天 9 点还没跑完 |
| 唯一性 | 主键是否重复     | 主键去重率 = 100%     | 订单明细表里同一个 `order_id=1001` 出现了两行 |
| 有效性 | 字段值是否合规    | 枚举范围、取值区间、格式校验   | `pay_amount=-99`，或 `order_status=abc` 不在合法枚举里 |

把维度落成可执行的**质量规则**，例如：

```text
order_id 非空率 = 100%                      # 完整性 + 唯一性
pay_amount >= 0                             # 有效性
分区数据量不能为 0                           # 完整性
用户ID重复率不能异常升高                      # 唯一性
昨日 GMV 波动不能超过历史均值的 ±30%          # 准确性（趋势）
order_status 只能落在合法枚举范围内           # 有效性
```

> [!note]
> 关键不在于“有规则”，而在于规则**接入了调度/质量平台、配了告警和阻断、且有人负责修复**。这条闭环在第五节的案例里完整展开。

### 2. 数据标准治理

数据标准解决“**定义一致**”的问题，是“可懂”的地基。它不是只管命名，而是把业务对象、字段、编码、口径、维度、指标都统一起来。

| 标准内容 | 解决的问题             | 例子                                                |
| ---- | ----------------- | ------------------------------------------------- |
| 命名标准 | 表名、字段名怎么叫         | 用户 ID 统一叫 `user_id`，不要一会儿叫 `uid`、一会儿叫 `member_id` |
| 字段标准 | 字段含义、类型、长度、精度是否统一 | `pay_amount` 统一表示实付金额，类型统一为 `decimal(18,2)`       |
| 编码标准 | 状态码、枚举值是否统一       | 订单状态统一为 `0=待支付，1=已支付，2=已取消，3=已退款`                 |
| 口径标准 | 同一个业务概念怎么算        | GMV 是否包含退款、运费、优惠券、税费，需要有唯一定义                      |
| 维度标准 | 分析维度怎么划分          | 时间维度按日/周/月，地区维度按省/市/区，渠道维度按统一渠道字典                 |
| 指标标准 | 指标名称、公式、粒度、周期是否统一 | 支付转化率 = 支付用户数 / 下单用户数，统计粒度为天                      |
| 格式标准 | 日期、金额、手机号等格式是否统一  | 日期统一 `yyyy-MM-dd`，金额保留 2 位小数，手机号按 11 位校验          |

> [!failure] 反例
> 用户 ID 不能一会儿叫 `user_id`、一会儿叫 `uid`、一会儿叫 `member_id`（除非确实代表不同对象）。口径不一致会直接导致下游 **join 错、指标对不上**，而且这种错往往很晚才被发现。

常见标准字段：

```text
用户ID：user_id      订单ID：order_id     商品ID：item_id
店铺ID：shop_id      支付时间：pay_time    创建时间：create_time
更新时间：update_time
```

> [!info]
> 指标口径的标准化（同名指标只有唯一定义）是数据标准最“值钱”的部分，展开见 [[职业化/数据工程/指标体系-业务度量方法.md]]。

### 3. 元数据治理

**元数据是“描述数据的数据”**，是“可懂、可追踪”的载体。工程实践中常按用途分为三类：

| 分类 | 说明 | 例子 |
| --- | --- | --- |
| **技术元数据** | 描述数据在系统里的技术形态，主要给数据开发、运维、平台使用 | 表结构、字段类型、分区、存储格式、任务调度信息、SQL 脚本、上下游血缘 |
| **业务元数据** | 描述数据在业务里的含义，主要给业务、分析、产品理解数据 | 字段业务含义、业务术语、指标口径、统计粒度、数据负责人、数据分级 |
| **管理元数据** | 描述数据如何被管理、使用和管控，也常被部分体系称为操作/运营元数据 | 访问权限、使用热度、变更记录、质量规则、生命周期状态、审计记录 |

> [!note]
> 阿里云 Dataphin 文档明确按用途分为 **技术元数据、业务元数据、管理元数据**；华为云 DataArts 文档则采用 **技术元数据、业务元数据** 两类，把部分管理信息放在标签、分类、密级等属性里。也就是说：**“技术 + 业务”是行业共识，“管理/操作元数据”是常见扩展分类**。参考：[阿里云 Dataphin 元数据中心](https://help.aliyun.com/zh/dataphin/fullmanaged/user-guide/metadata-center/)、[华为云 DataArts 元数据简介](https://support.huaweicloud.com/usermanual-dataartsstudio/dataartsstudio_01_0802.html)。

衡量元数据是否到位有个直观标准：一个人看到 `dws_trade_user_1d`，应该能立刻读出它的**主题（交易）、粒度（用户）、更新周期（1 天）、负责人、上下游依赖**。

> [!example] 常见工具
> Apache Atlas、DataHub、Amundsen、阿里 DataWorks 数据地图。核心能力都是**元数据采集 + 血缘解析 + 检索**。血缘太重要，单独放第三节讲。

### 4. 数据资产治理

数据资产治理解决“**找得到、看得懂、用得好**”（可找）的问题，把“数据”当“资产”来运营。包括：

- 数据地图、主题域管理、数据服务目录
- 表资产分级（核心 / 重要 / 一般）、热表识别、负责人管理
- 低价值表识别与下线

> [!example] 典型场景
> 某张表 90 天无人查询、无下游依赖、却占用大量存储 → 进入**下线评估流程**（同时关联成本治理）。

| 对比项 | 元数据治理 | 数据资产治理 |
| --- | --- | --- |
| 核心视角 | 管数据的“说明书” | 管数据资产的“运营” |
| 关注粒度 | 更关注表、字段、指标、血缘等具体信息 | 更关注主题域、核心表、热表、低价值表等全局资产 |
| 主要问题 | 这张表是什么？字段什么意思？从哪来、到哪去？谁负责？ | 哪些表有价值？哪些表常用？哪些重复建设？哪些该下线？ |
| 典型动作 | 补表说明、字段说明、指标口径、血缘、负责人 | 资产分级、热表识别、低价值表清理、数据目录运营 |
| 目标 | 让单张表**看得懂、追得清** | 让全局数据**找得到、用得好、管得住** |

### 5. 数据安全治理

数据安全治理解决“**谁能看、谁能用、怎么用、出了问题能不能追责**”（可控）的问题，核心是**分级分类 + 最小权限 + 脱敏加密 + 审计追踪**。

![[数据安全治理逻辑-流程图.png]]

行业里没有唯一固定清单，但 DAMA、数据安全法/PIPL、各云厂商数据治理平台的实践基本都会覆盖下面几类：

| 大类      | 包含内容                    | 解决的问题              | 例子                                    |
| ------- | ----------------------- | ------------------ | ------------------------------------- |
| 数据识别与分级 | 数据分类分级、敏感数据识别           | 先知道哪些数据重要、哪些数据敏感   | 普通数据 / 重要数据 / 核心数据；识别手机号、身份证号、银行卡号    |
| 权限与访问控制 | 权限审批、角色授权、行列级权限、最小权限    | 控制谁能看、谁能用、能用到什么程度  | 运营只能看脱敏手机号，财务只能看订单金额，开发不能直接导出明文数据     |
| 数据保护    | 数据脱敏、数据加密、密钥管理          | 即使数据被访问或传输，也降低泄露风险 | 手机号 `138****8888`；存储加密、传输加密           |
| 数据流转管控  | 数据导出、接口调用、第三方共享、出境管控    | 控制数据从平台流向外部的过程     | 导出审批、接口鉴权、共享留痕、跨境传输评估                 |
| 审计与追踪   | 查询日志、下载日志、权限变更日志、异常访问告警 | 出问题后能追溯谁在什么时候做了什么  | 某账号凌晨批量下载用户数据，触发异常告警并可追踪操作记录          |
| 安全合规管理  | 法规对齐、制度流程、审批留痕、责任机制     | 满足法律、监管和公司制度要求     | 对齐《数据安全法》《个人信息保护法》（PIPL），建立审批、留痕、问责机制 |

常见敏感字段与脱敏方式：

```text
敏感字段：手机号、身份证号、银行卡号、详细地址、邮箱、设备号、行为轨迹
脱敏示例：
  手机号  → 保留前三后四（138****8888）
  身份证  → 脱敏出生日期等中间位
  地址    → 按省/市/区聚合
  用户ID  → hash 或 token 化
```
常用脱敏方式

|处理方式|例子|是否可逆|适合场景|
|---|---|---|---|
|**加密 encryption**|`device_id` → 密文|**可逆**，有密钥就能解密|业务系统需要在授权场景下还原设备 ID|
|**哈希 hash**|`device_id` → 固定 hash 值|**通常不可逆**|做去重、归因、关联分析，但不需要还原明文|
|**加盐哈希 salted hash**|`device_id + salt` → hash|**不可逆性更强**|防止被撞库反推|
|**Token 化 tokenization**|`device_id` → 随机 token|**可逆**，但依赖映射表|对外共享或跨系统使用替代 ID|
|**打码 masking**|`abc123xyz` → `abc****xyz`|**不可逆**|页面展示、人工查看|
> [!warning] 合规背景
> 数据安全直接关联《数据安全法》《个人信息保护法》（PIPL）。面试提到“**分级分类 + 最小权限 + 审计可追溯**”会是明显加分项。

### 6. 成本治理

成本治理解决“**用得起**”（可负担）的问题，本质是**在满足业务 SLA 的前提下，减少存储、计算、调度、资源和重复链路带来的浪费**。

成本治理可以分两层理解：

- **治理对象**：真正产生成本的地方，比如存储、计算、调度、云资源、重复建设。
- **治理手段**：用来发现和约束成本的方法，比如成本可视化、预算、配额、预警、复盘。

| 治理方向   | 核心内容                    | 定位                    |
| ------ | ----------------------- | --------------------- |
| 成本可视化  | 账单、资源、任务、团队维度看板         | 先看清钱花在哪里、谁花的          |
| 存储治理   | 冷热分层、生命周期、无用数据清理、小文件治理  | 解决数据存太多、存太久、存得不合理     |
| 计算治理   | SQL 优化、任务优化、资源参数优化、队列治理 | 解决 SQL/任务消耗资源过高       |
| 调度治理   | 无效任务下线、重复任务合并、频率优化      | 解决任务跑得太频繁、重复跑、无效跑     |
| 数据资产治理 | 模型复用、血缘分析、指标统一、冗余链路治理   | 解决重复建设、重复计算、公共层复用差    |
| 云资源治理  | 弹性伸缩、实例优化、闲置资源回收        | 解决机器、集群、实例等资源闲置或配置不合理 |
| 管理机制   | 预算、配额、预警、责任人、准入审批       | 给成本设置边界，避免无限制增长       |
| 持续运营   | 成本监控、优化复盘、收益评估、闭环治理     | 防止成本优化后反弹，形成长期机制      |

> [!note]
> 面试里可以按这个顺序讲：**先用成本可视化发现问题，再围绕存储、计算、调度、资产和云资源做优化，最后用预算、配额、预警和复盘形成持续闭环**。

## 三、数据血缘：贯穿治理的“底座能力”

> [!note]
> 血缘原本属于元数据，但它太重要，单独拎出来。**面试只要提到“影响分析”“口径追溯”，本质都是血缘**。

**数据血缘**记录数据从源到目标的流转关系，分两个粒度：

- **表级血缘**：A 表的数据来自哪些表、又流向哪些表。
- **字段级血缘**：某字段由哪些上游字段加工而来（更精细，排障更准）。

血缘建设一般是自动采集/解析为主，人工维护为辅。
血缘的三大核心价值：

1. **影响分析（改之前）**：改字段/口径前，先看会影响哪些下游表、指标、看板、接口。
2. **问题溯源（错之后）**：指标异常时，沿血缘从下游反查到出问题的上游节点。
3. **资产盘点（平时）**：识别孤儿表（无下游）、循环依赖、超长链路风险。

## 四、数据治理在数仓分层中的体现

治理不是悬空的规则，它**落在数仓的每一层里**。典型分层：

```text
ODS ──► DWD ──► DWS ──► ADS
```

| 分层      | 定位           | 治理重点                          |
| ------- | ------------ | ----------------------------- |
| **ODS** | 原始数据接入、保真    | 接入完整性、分区规范、源表变更感知、原始字段保留、延迟监控 |
| **DWD** | 明细事实、业务过程标准化 | 统一命名、统一口径、主键唯一、维度退化、清洗规则      |
| **DWS** | 公共汇总、指标复用    | 统一统计粒度、公共指标沉淀、避免重复计算、主题域一致    |
| **ADS** | 业务应用交付       | 指标准确性、查询性能、口径说明、下游影响通知        |

> [!tip]
> 一句话：**好的数仓分层本身就是数据治理的一部分**。分层建模的完整方法论见 [[职业化/数据工程/数据建模方法论全景 从底层理论到顶层工程.md]]。

## 五、案例串讲：订单数据质量治理闭环

> [!example] 主力故事
> 这个案例把前面的“质量维度 → 规则 → 告警 → 闭环”一次性串起来，面试时可作为你的“主力故事”。

有一张订单明细表 `dwd_trade_order_detail_di`，核心字段：

```text
order_id / user_id / item_id / shop_id
order_amount / pay_amount / order_status
create_time / pay_time / dt
```

### 1. 发现问题（对应六大维度）

| #   | 问题                  | 违反维度 | 业务影响    |
| --- | ------------------- | ---- | ------- |
| 1   | `order_id` 重复       | 唯一性  | 订单数虚高   |
| 2   | `pay_amount` 出现负数   | 有效性  | GMV 失真  |
| 3   | `pay_time` 为空但状态已支付 | 一致性  | 状态与事实矛盾 |
| 4   | 分区 `dt` 数据量突然下降     | 完整性  | 数据丢失    |
| 5   | 上游字段类型变化            | 准确性  | 任务失败    |
| 6   | 测试订单未过滤             | 有效性  | 污染指标    |

### 2. 建立规则 + 分级告警

```text
order_id 非空率 = 100% 且唯一率 = 100%
pay_amount >= 0
已支付订单 pay_time 不为空
每日订单量波动不超过历史均值的合理阈值
order_status 必须在合法枚举范围内
过滤测试用户/测试店铺
```

| 等级 | 场景 | 动作 |
| --- | --- | --- |
| **P0** | 核心指标错误 | 立即告警 + **阻断下游**（不让脏数据流入 DWS/ADS） |
| **P1** | 数据延迟或部分异常 | 告警负责人，限时修复 |
| **P2** | 非核心字段异常 | 记录并定期治理 |

### 3. 治理结果

通过“规则 + 阻断 + 责任人”，**把错误数据拦截在进入 DWS、ADS 和 BI 看板之前**，避免业务误判。这就是数据质量治理“**防患于未然**”的核心价值，也是从“数据能跑出来”升级到“数据可信”的关键一跃。

## 六、数据治理的落地闭环

治理是长期运营，必须形成闭环，而不是一次性冲刺：

```text
盘点资产 ─► 定标准 ─► 建规则 ─► 接监控 ─► 责任到人 ─► 持续优化 ─┐
   ▲                                                          │
   └──────────────────── 复盘沉淀 ◄───────────────────────────┘
```

落地七步：

1. **盘点数据资产**：有哪些表、谁在用、谁负责。
2. **梳理核心链路**：优先治理核心指标和核心表（二八原则）。
3. **制定标准规范**：命名、字段、分层、口径、权限。
4. **建立质量规则**：完整、准确、一致、及时、唯一、有效。
5. **接入监控告警**：任务失败、数据波动、延迟、空分区。
6. **责任到人 + 闭环**：问题发现 → 修复 → 复盘 → 预防。
7. **成本持续优化**：清理无用表、优化任务与存储。

> [!warning] 关键认知
> 数据治理**不是一次性项目，而是长期运营**。面试时强调“**闭环**”和“**持续**”，比罗列一堆动作更有说服力。

## 七、数据研发在数据治理中的职责

数据研发是治理的**第一执行人**，典型职责（对应“六可”理解会更清晰）：

- 建设规范化的数据模型、维护表/字段元数据 → 可懂
- 编写质量校验规则、处理数据异常和任务失败 → 可信
- 推动指标口径统一 → 可用
- 支持权限、脱敏与审计 → 可控
- 优化 SQL/调度性能、管理数据生命周期 → 可负担

> [!quote]
> **一个优秀的数据研发，不只是能把数据跑出来，更要保证数据长期稳定、准确、低成本地服务业务。**

## 八、面试常问问题（含答题思路）

> [!tip] 答题套路
> **先给定义/框架 → 再落到具体动作 → 最后点出闭环或亲历经验**。能讲出“我排过的一次线上问题”比背概念强十倍。

### 1. 什么是数据治理？

数据治理是为了保障**数据质量、标准、安全、资产价值和使用效率**而建立的一套**长期机制**，核心目标是让数据**可信、可懂、可找、可用、可控、可负担**，业界对应 DAMA-DMBOK 框架。

### 2. 数据治理包括哪些方面？

主要包括**数据质量、数据标准、元数据、数据安全、数据资产、数据生命周期与成本治理**，其中**数据质量是核心，血缘是底座**。

### 3. 如何做数据质量监控？

先识别**核心表和核心指标**（二八原则），再从**完整、准确、一致、及时、唯一、有效**六个维度设计规则，接入调度/质量平台，配置**分级告警和阻断策略**，并建立**责任人 + 修复闭环**。

### 4. 数据质量异常怎么排查？

**从链路上游到下游逐段排查**：

```text
源系统 ─► 数据接入 ─► ODS ─► DWD ─► DWS ─► ADS ─► BI
```

重点看：源数据是否异常、任务是否失败、分区是否缺失、SQL 逻辑是否变更、字段类型是否变化、过滤条件是否错误、上下游口径是否一致。**这里最能体现你是否真的排过线上问题**——准备一个具体例子。

### 5. 如果一个核心指标突然异常，你怎么处理？

**第一步先判断是“业务真实波动”还是“数据问题”**——对比历史趋势、上游数据量、任务状态、分区产出、SQL/源系统变更和相关指标。
确认是数据问题后：**告警 → 定位（沿血缘）→ 修复 → 回刷数据 → 同步受影响业务方 → 复盘预防**。

### 6. 元数据和数据血缘有什么作用？

**元数据**帮人理解表和字段含义（可懂）；**血缘**帮人追踪来源和影响范围。字段口径变化时，可通过血缘做**影响分析**，定位受影响的下游表、指标、看板和接口。

### 7. 如何做数据成本治理？

从**存储和计算**两方面入手：
- **存储**：清理无用表、设置生命周期、冷热分层。
- **计算**：优化 SQL、减少重复任务、避免全表扫描、合理分区、减少大 shuffle、合并小文件、复用公共层。

### 8. 数据治理和数据仓库建设有什么关系？

数据仓库是数据治理的**重要载体**：良好的分层、主题域、公共维度、统一指标层和规范命名，本身就是治理落地；而治理反过来保证数仓**长期可维护、可信、可复用**。两者是“一体两面”。
