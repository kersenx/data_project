这份报告的核心观点只有一句话：**大数据技术不是若干工具的堆叠，而是对一组持续升级的工程矛盾的分阶段回应。**最早，Google 在 GFS、MapReduce、Bigtable 里明确写出了这些矛盾：便宜机器经常坏、文件巨大、追加写多、计算要跨成百上千台机器并自动恢复、同一份数据既要支持批处理又要支持更低延迟的服务；随后 Spark RDD 论文又补上了下一阶段的矛盾——MapReduce 类系统对“数据复用”不友好，磁盘 I/O、复制和序列化会主导执行时间。

因此，理解大数据最有效的方法，不是按 Hadoop、Spark、Flink、ClickHouse 分散记忆，而是按**矛盾链**来学：  
**存储扩展**解决“数据放不下”；**分布式批计算**解决“单机算不动”；**资源管理解耦**解决“多框架抢资源”；**内存复用与 DAG**解决“多阶段计算太慢”；**消息总线与状态流处理**解决“实时性”；**MPP 与列式 OLAP**解决“交互式分析”；**湖仓表格式**解决“数据湖不可靠、难治理”；**平台工程化与 AI 数据工程**解决“从可运行到可运营、从 BI 到智能应用”。这些目标分别对应 HDFS/YARN、MapReduce、Hive、Spark、Kafka、Flink、Trino/Presto、ClickHouse/Doris/StarRocks、Iceberg/Hudi/Delta Lake、以及元数据/血缘/质量/Feature Store/向量检索等能力。

从面试表达看，最加分的方式不是“这个组件怎么用”，而是“**为什么它会出现、它替代了谁、保留了什么、牺牲了什么**”。例如，Spark 并不是“比 MapReduce 快的框架”这么简单，而是通过数据复用、DAG 执行和优化器，把“批处理”和“交互式 SQL”纳入同一执行栈；Flink 也不只是“实时框架”，而是用事件时间、状态、Checkpoint 与 Watermark，把“无界流的一致性计算”工程化了。

为便于系统学习，整份报告按六条主线组织：**为什么出现、底层原理、核心平台、工程化与 AI、技术选型、面试与学习路径**。文末附有**高频题清单、技术选型对比表、学习路线图、术语索引、复习清单、图示素材包**，可以直接作为复习底稿、培训提纲或面试讲稿。

## 大数据为什么出现与如何演进

> [!info] 本节覆盖
> 大数据技术为什么出现，以及从 Google 论文、Hadoop、Spark/Flink、OLAP 到湖仓与 AI 数据工程的演进脉络。

> [!tip] 配图说明
> 本节配图为技术演进时间轴，按“Google 论文时代 → Hadoop 生态时代 → 统一计算与实时时代 → 交互式 OLAP 时代 → 湖仓与 AI 数据工程时代”五段展开。关键转折点包括 SQL 化、资源解耦、内存复用、实时化、表格式、AI 数据服务。图注：**每一代技术都在解决上一代暴露出来的核心矛盾。**

![[assets/bigdata-evolution/02-evolution-timeline.png]]

> [!summary] 本节速读
> - 单机系统的瓶颈不只是容量，而是存储、计算、备份、恢复、实时性和协作边界同时到达上限。
> - 技术演进可以看成“分布式存储 → 并行批计算 → SQL 化 → 资源解耦 → 内存复用 → 实时化 → 湖仓治理 → AI 数据服务”。
> - 记忆关键：每一代技术都在补上一代系统暴露出来的缺口。

### 传统单机的边界

传统单机数据库与传统数仓的最大优势，是**单机事务一致性强、模型稳定、维护简单**；它们的最大局限，也恰恰来自“单机”本身。当数据量进入 TB/PB，单机存储、CPU、内存、网卡、备份窗口和恢复时间都会成为硬边界；当计算跨多个步骤反复扫描同一份数据时，单机和早期批引擎的磁盘 I/O 成本会迅速失控；当业务既要求“昨天的报表”又要求“分钟级甚至秒级看板”时，传统夜间批处理链路就会被打穿。Google 设计 GFS 和 MapReduce 时明确指出：组件失效不是例外而是常态，文件往往巨大，且大量工作是对海量原始数据做并行处理；Spark RDD 论文则指出，迭代算法和交互式数据分析对“数据复用”的需求，使得只会一轮一轮落盘的框架变得低效。

### 4V/5V 的工程翻译

如果用“4V/5V”来记忆，大数据通常被概括为规模、速度、多样性，以及真实性/价值等维度；
但工程上更重要的是把这些口号翻译成真正的问题：  
**存储**要能横向扩展并容忍节点故障；  
**计算**要能并行并支持失败恢复；  
**调度**要能让不同框架共享资源；  
**查询**要能让分析工程师使用 SQL；  
**实时**要能处理无界流和乱序事件；  
**治理**要把元数据、血缘、质量、安全和成本纳入平台能力。Google 论文、HDFS/YARN/Hive/Spark/Flink/Kafka/Trino 与 Lakehouse 文档共同证明，后续几乎所有主流系统，都围绕这六类问题演化出来。

### 问题驱动时间线

可以把技术演进理解成下面这条时间轴。它不是精确产品史，而是**问题驱动的世代更替**：

```text
Google 论文时代
GFS  →  MapReduce  →  Bigtable
  │         │             │
  └── 分布式存储 ── 并行批计算 ── 面向结构化海量数据

Hadoop 生态时代
HDFS / MapReduce  →  Hive  →  YARN
  │                    │        │
  └── 开源实现GFS思想 ─ SQL化 ─ 资源管理解耦

统一计算与实时时代
Spark / Spark SQL  →  Kafka  →  Flink
  │                     │        │
  └── DAG、内存复用 ── 数据总线 ─ 状态流处理

交互分析与实时OLAP时代
Presto/Trino  →  ClickHouse / Doris / StarRocks
  │                     │
  └── 查询加速、联邦查询 ─ 列式MPP、近实时指标服务

湖仓与AI数据工程时代
Iceberg / Hudi / Delta Lake  →  云原生数据平台  →  Feature Store / Vector DB / RAG
```

这条技术演进链背后的“代际逻辑”非常重要。MapReduce 解决的是**能不能分布式地算**；Hive 解决的是**能不能用 SQL 来写**；YARN 解决的是**能不能把资源管理从某个计算框架里拆出来**；Spark 解决的是**多阶段和交互式计算为什么这么慢**；Kafka 和 Flink 解决的是**数据要不要等到第二天**；Trino 和实时 OLAP 则解决的是**分析师提一个 SQL 为什么要等十分钟甚至更久**；Iceberg/Hudi/Delta Lake 解决的是**把数据放进对象存储之后，如何让它重新获得“表”的语义**。这也是你回答“如何理解大数据技术演进”时最应该抓住的主线。

### 面试总述

一个很适合面试的总述模板是：  
“**大数据技术演进，本质上是从‘先扩容存储’到‘再扩容计算’，再到‘统一资源、统一 SQL、统一批流、统一数据底座’，最后走向可治理、可观测、可服务 AI 的平台化过程。**”这句话之所以成立，是因为每一步都能在官方论文或官方文档里找到对应的工程约束与架构回应。

> [!quote] 面试一句话
> 大数据技术演进不是从 Hadoop 背到 Flink，而是从“数据放不下、算不动、查不快、管不好、服务不了 AI”这条问题链讲起。

## 存储与计算的第一性原理

> [!info] 本节覆盖

> [!tip] 配图说明
> 本节配图为“存储与计算双架构图”：左侧展示 HDFS 的 NameNode、DataNode、Block、副本和元数据压力，右侧展示 MapReduce/Spark 的 Map、Shuffle、Reduce、DAG、Stage、Task 与 Shuffle 成本。图注：**分布式系统的第一性问题，是把数据放对、把计算拆开、把失败恢复纳入运行时。**

![[assets/bigdata-evolution/03-storage-compute.png]]

> [!summary] 本节速读
> - HDFS 的核心是元数据和数据分离：NameNode 管目录与映射，DataNode 管真实块数据。
> - 列式格式、分区裁剪、谓词下推和压缩，本质都在减少真实读取的数据量。
> - MapReduce 让分布式批计算标准化；Spark 则用 DAG、缓存和优化器减少重复 I/O。

### HDFS：元数据和数据分离

HDFS 的核心不是“把文件分散到多台机器上”这么简单，而是把**元数据**和**数据块**分离：一个 NameNode 负责命名空间、文件到 Block 的映射，以及 Block 到 DataNode 的映射；多个 DataNode 负责真正存放数据块并提供读写服务。HDFS 明确采用主从架构，文件会被切成一个或多个 block 存到多个 DataNode 上，副本数也由 NameNode 记录；而且用户数据**不会流经 NameNode**，这样才能避免把元数据节点做成数据通道瓶颈。NameNode 通过 EditLog 记录元数据变更，通过 FsImage 保存命名空间快照，并在启动或阈值触发时做 checkpoint。

这套设计的通俗理解是：**NameNode 像“图书馆总目录”，DataNode 像“具体书架”，Block 像“拆开的书册页码段”**。目录要尽量小而准，书页则分散放到很多书架，并放多份副本来防丢。因为 NameNode 要把整个文件系统命名空间和 block map 放在内存里，小文件过多会带来元数据膨胀、RPC 放大、并发目录操作变重等问题，这就是工程上常说的小文件问题。HDFS 文档也明确指出，NameNode 会在内存中维护命名空间与 block map，而 Federation 的目标之一就是提升命名空间扩展性。

### HDFS 与对象存储

HDFS 与对象存储的差异，面试里非常高频。HDFS 是面向文件系统语义设计的，目录与 rename 是一等能力；而 S3 等对象存储本质上把数据作为 object 放在 bucket 中，通用 bucket 还是**扁平命名空间**，所谓“文件夹”通常只是前缀展示。Hadoop 官方在 S3A 文档里明确写到：对象存储并不真正支持 rename，模拟 rename 的方式通常是 copy + delete，因此成本与数据量近似成正比；AWS 也明确说明 S3 是对象存储，bucket 中对象是核心资源，通用 bucket 是 flat structure；Google Cloud 则专门把 hierarchical namespace 作为一个可选能力来介绍，说明“层级目录”和“原子 rename”并不是对象存储的默认前提。

所以在工程取舍上，**HDFS 更像“本地磁盘的分布式放大器”，对象存储更像“带高可扩展元数据与 API 的远程对象池”**。前者更适合以文件系统语义为中心的老生态，后者更适合云上弹性、低运维和多计算引擎共享。真正让对象存储适合分析系统的关键，并不只是“便宜和大”，而是后续由 Iceberg/Hudi/Delta Lake 提供的**表语义、快照、事务和元数据管理**。

### 存储格式

存储格式层面，行式与列式的差别也必须从“为什么”来理解。行式存储擅长点查和整行更新，因为同一行的字段被放在一起；列式存储擅长分析型扫描，因为只需读相关列即可。ORC 把文件主体组织为 stripe，每个 stripe 自包含索引、数据和 stripe footer，而且索引与数据按列拆分，只读需要列即可；ORC 的 footer 里还有文件级和 stripe 级统计，row group 级索引里还能记录列统计与位置。Parquet 同样以 row group 和 column chunk 组织数据，并通过统计、字典、page index、bloom filter 等机制支撑 predicate pushdown 和更细粒度的数据跳过。

这也是为什么在 Hive/Spark/Trino/ClickHouse 体系里，你几乎总会听到**列裁剪、谓词下推、分区裁剪、压缩**这些词。它们本质上都在做一件事：**减少需要真正读取的数据量**。ClickHouse 官方说得非常直接：最快的读法，就是“不读”；因此它在主键索引、projection、skipping index、压缩和向量化执行上同时发力。

### MapReduce

再看计算。MapReduce 之所以重要，不是因为它的 API 简单，而是因为它第一次把“**并行化、故障恢复、数据分发、跨机器通信**”这些麻烦活统一包进了运行时。Map 阶段把输入记录变成中间 key/value；Shuffle 按 key 重新分区并把中间结果聚到一起；Reduce 再按 key 合并输出。Google 论文明确指出，用户只需要写 map 和 reduce，运行时会负责输入分片、调度、失败处理和必要的机器间通信。

单机计算为什么不够，在现在面试里更好的答法是：**不是 CPU 不够，而是“数据位置、并行度、失败恢复、资源隔离、数据复用”这些问题单机根本不存在，所以单机经验一旦进集群，很多结论就失效了。**MapReduce 解决了“能分布式跑起来”，但它把复杂作业切成多个相对独立的阶段，阶段之间大量落盘；Spark RDD 论文正是因为看到这件事，才提出基于粗粒度转换和 lineage 的 RDD，让中间结果可以显式保留在内存中，在丢分区时按血缘重算而不是全量复制。

### Spark 与 Shuffle

Spark 为什么普遍比 MapReduce 快，可以概括为三点。
**1. 中间结果的存储介质和复用(最主要)**  
MapReduce 每个 job 的 Map 输出必须写本地磁盘,Reduce 再拉取;多个 job 串联时,中间结果还要落回 HDFS(带副本、带网络)。Spark 的 RDD/DataFrame 可以用 `cache`/`persist` 把中间结果留在内存,迭代计算和多阶段 pipeline 不必反复读写磁盘。对机器学习、图计算这类要多轮迭代的场景,差距能到数量级。
**2. 执行模型:DAG vs 固定两阶段**  
MR 只有 Map→Reduce 两个阶段,稍复杂的逻辑就得拆成多个 job 首尾相接,每次衔接都落盘。Spark 把整条计算链表达成一张 DAG,由 DAGScheduler 按宽/窄依赖切分 stage:

- 窄依赖(map、filter)可以在一个 stage 内 **pipeline** 连续执行,中间不落盘、不物化;
- 只有遇到宽依赖(shuffle)才切 stage。

所以 Spark 是"一整条链一起优化",而 MR 是"一步一步各自为政"。Catalyst/Tungsten 进一步做了谓词下推、列裁剪、代码生成等优化。

**3. 进程 vs 线程(启动开销)**  
MR 每个 task 是一个独立 JVM 进程,task 多时反复启停 JVM,开销大。Spark 的 Executor 是常驻进程,task 以**线程**方式跑在里面,复用 JVM,调度更轻。

**但要诚实,Spark 不是永远更快:**

- Shuffle 阶段 Spark 同样要落盘(sort-based shuffle 写磁盘),这块没有魔法;
- 内存放不下时会 spill 到磁盘,优势缩水,甚至可能 OOM;
- 对**一次性、单遍扫描的超大批处理**(数据远大于内存、纯 IO 密集),Spark 相对 MR 的优势没那么明显。

面试一句话总结:**Spark 快在"内存复用 + DAG 全局流水线优化 + 进程复用"三点,本质是减少了不必要的磁盘/网络 IO 和重复启动开销;而在必须 shuffle 落盘的环节,两者没有本质区别。**

理解 Shuffle 的最好方式，不是死背“宽依赖很慢”，而是把它看成一次**按分区规则重新组织数据的全局重排**。Spark 文档写得很清楚：action 会通过一组 stage 执行，而 stage 之间正是由 distributed shuffle operations 分隔开的。只要跨 key 重分布、重新排序或重新聚合，就会引发网络传输、序列化/反序列化、磁盘 spill、以及容易被数据倾斜放大的尾部任务。这也是为什么 Spark 的 AQE 会尝试在运行时把 sort-merge join 改写成 broadcast hash join，并通过 local shuffle reader 减少不必要的数据读取与网络流量。

### 概念速记

下面这张“概念三联表”，适合记忆，也适合面试时快速组织语言：

| 概念                   | 通俗解释                 | 技术解释                                                 | 面试表达                                       |
| -------------------- | -------------------- | ---------------------------------------------------- | ------------------------------------------ |
| Block 与副本            | 把大文件拆小块放到多台机器上，还多存几份 | HDFS 文件切 block，NameNode 维护映射与 replication factor     | “HDFS 用块和副本把扩展性与容错解耦，核心是元数据/数据分离。”         |
| 小文件问题                | 书太薄太多，目录先爆了          | NameNode 维护 namespace 和 block map 于内存，小文件会放大元数据与 RPC | “小文件不是磁盘容量问题，而是元数据与 Namenode 压力问题。”        |
| Shuffle              | 把同类货物从各仓库重新归集        | 依 key 重分区，跨节点交换与排序/聚合，形成新的 stage 边界                  | “Shuffle 的本质是全局重分布，所以慢点在网络、磁盘和倾斜。”         |
| Lineage 与 Checkpoint | 丢了一块就按配方重做           | RDD 记录转换血缘；检查点把中间结果外部化，缩短恢复链路                        | “Spark 的容错优先靠血缘重算，链路太长或代价太大时才 checkpoint。” |

表中结论综合 HDFS 架构文档、MapReduce 论文、RDD 论文、Spark SQL 论文与 Spark 官方调优文档整理。

> [!quote] 面试一句话
> 分布式系统先解决“数据怎么放、任务怎么拆、失败怎么恢复”，性能优化再围绕“少读、少传、少落盘、少倾斜”展开。

### Hadoop 与 Hive

先看 Hadoop 生态。把 Hadoop 说成“HDFS + YARN + MapReduce”并没有错，但这只是内核，不是生态。HDFS 提供分布式存储；YARN 把资源仲裁交给 ResourceManager，把每机执行代理交给 NodeManager，把单应用执行控制交给 ApplicationMaster；Hive 则把 SQL 编译成底层执行图并依赖 Metastore 保存表与分区元数据。Apache Hive Developer Guide 明确写到：Hive 主要由 SerDe、MetaStore、Query Processor 组成，而 Query Processor 的职责是把 SQL 转为 map/reduce job graph；Hive 配置文档也明确给出执行引擎可以是 `mr`、`tez` 或 `spark`。

Hive 的定位从来不是“快”，而是“**让数据团队用 SQL 组织大规模离线加工**”。这意味着它非常适合做离线数仓开发、长链路 ETL、指标口径沉淀和可追溯的批处理，但并不适合低延迟交互式分析。Hive Metastore 的价值也不只是“存元数据”，而是把“表”这件事真正从文件系统上抽象出来——没有 Metastore，你只有目录和文件；有了 Metastore，你才有库、表、分区、列、SerDe、统计信息，以及后续的权限与治理基础。

离线数仓分层方面，国内团队常用 ODS、DWD、DWS、ADS 这套词汇。阿里云文档将 ODS 定义为几乎不做加工、与源系统保持基本一致的数据准备区；维度建模则遵循 Kimball 思想，围绕维度表、事实表、汇总表和应用表组织模型。重要的不是背缩写，而是理解它们背后的职责：ODS 保真、DWD 规范化明细、DWS 面向主题汇总、ADS 直接为应用服务。

### Spark

Spark 的定位，是“**统一分析引擎**”。官方主页与文档都强调，它既做数据工程，也做 SQL、流处理、机器学习与图计算；Cluster Overview 则说明 driver 有独立 Web UI，可查看 tasks、executors 和 storage usage。Spark SQL 论文进一步解释了 DataFrame 的意义：它让关系式处理与 Spark 程序式 API 可以无缝混用，并经过 Catalyst 分析、逻辑优化、物理规划和代码生成；Spark 官方文档则指出，DataFrame/Dataset 享受 Catalyst 与 Tungsten 的优化收益。

从工程实践看，Spark 最值得面试展开的点有五个。  
其一，**RDD / DataFrame / Dataset**：RDD 强在通用性与显式控制；DataFrame 强在结构化与优化器友好；Dataset 试图把类型安全与优化器收益结合起来。  
其二，**Job / Stage / Task**：理解“stage 被 shuffle 边界切开”比死记名词更重要。  
其三，**Join 策略**：BROADCAST、MERGE、SHUFFLE_HASH 等策略可以通过 hint 提示，优先级也是官方文档明示的。  
其四，**AQE**：运行时根据统计信息把 sort-merge join 改写成 broadcast hash join，并借助 local shuffle reader 进一步降成本。  
其五，**调优入口**：分区数、文件大小、缓存、广播阈值、GC、数据倾斜、Executor 资源和 Spill 行为。

### Flink

Flink 的定位则不同。它本质上是面向**状态化流处理**的分布式系统，虽然后来也形成了流批一体语义。官方架构文档说明 Flink 可运行在 YARN、Kubernetes、Standalone 等环境；Stateful Stream Processing 文档说明，它通过**流重放 + Checkpoint**容错：Checkpoint 为每个输入流与每个算子状态标记一个一致点，恢复时回放流并恢复状态，从而保持 exactly-once 语义；Savepoint 是手动触发的程序快照，用于升级、迁移与受控恢复。

Flink 为什么适合实时计算，核心在于它把过去“实时近似脚本化”的事情，升级成了“**时间语义 + 状态语义 + 一致性语义**”三个维度同时可控的系统。官方文档给出三类时间特征：Processing Time、Ingestion Time、Event Time；官方博客则把 Watermark 定义为“一个时间 t，表示系统不再期待早于 t 的事件”，水位线一旦越过窗口结束时间，相关窗口就可以被关闭与计算。配合迟到数据处理、side output、状态后端和反压观测，Flink 才真正能够承载实时数仓、实时风控和复杂 CEP 之类的场景。

### Kafka 与实时链路

Kafka 在实时架构里的定位，最准确的说法是：**高吞吐、可回放、分区化的日志系统与消息总线**。Kafka 设计文档介绍了 topic、partition、producer、consumer、consumer group 等基本抽象；同一 consumer group 中，一个 partition 只会被一个 consumer 实例消费，因此分区数决定了组内水平并行的上限。Kafka 还保留消息一段时间，消费者可以按 offset 重放，这使它比传统队列更适合作为实时数仓的数据中枢。对变更数据捕获，Debezium 官方说明它是 Kafka Connect 的一组 source connector，利用数据库自身 CDC 特性做 log-based CDC；Canal 明确自己基于 MySQL binlog；Flink CDC 则把实时与批集成进一步统一到流式数据集成工具里。

一个经典实时链路可以用下面这个文本图来记忆：

```text
业务库(MySQL/Postgres)
        │
        │ binlog / WAL
        ▼
CDC（Debezium / Canal / Flink CDC）
        │
        ▼
Kafka（Topic / Partition / Offset）
        │
        ▼
Flink（清洗 / 维表关联 / 窗口聚合 / 状态）
        │
        ├────────► 实时指标服务（ClickHouse / Doris / StarRocks）
        │
        └────────► 湖仓表（Iceberg / Hudi / Delta）
```

这条链路的好处在于职责清晰：CDC 负责“捕获变化”，Kafka 负责“缓冲与解耦”，Flink 负责“计算与一致性”，OLAP 或 Lakehouse 负责“服务化落地”。Kafka 并不是“实时计算框架”，Flink 也不是“消息队列替代品”。很多候选人答错这两个定位，面试官会立刻判断体系感不足。

### OLAP 与湖仓

再看交互式分析与实时 OLAP。Hive 与 Spark SQL 更像**通用计算引擎上的 SQL 层**；Trino/Presto 更像**联邦查询与交互式分析引擎**；ClickHouse / Doris / StarRocks 更像**为低延迟聚合分析专门优化的列式 MPP 数据库**。Trino 官方文档明确它是 distributed query engine，由 coordinator 和 workers 组成；Presto 官方首页强调其面向 fast、reliable、efficient 的 interactive / ad hoc 查询；Doris 和 StarRocks 官方都强调 MPP、实时分析、高并发与向量化执行。

ClickHouse 为什么快，可以直接按官方文档回答：  
一是**主键索引、projection、skipping index**帮助跳过大量不需要读的行；  
二是**列式压缩**让存储更小、I/O 更低；  
三是**向量化执行**按批处理行，提升 CPU cache 命中并利用 SIMD；  
四是**多 lane 并行与分片集群**让它既能纵向扩 CPU，也能横向扩节点；  
五是**merge-time computation**把部分工作前移到后台合并流程，减轻查询瞬时压力。

关于数据湖、数据仓库与湖仓一体，最简洁的理解是：  
**数据仓库**强调模式稳定、治理严格、服务分析；  
**数据湖**强调原始数据低成本汇聚与多样性；  
**湖仓一体**则试图在数据湖存储上重新获得“表”的可靠性。Delta 官方首页直接把自己定义为构建 Lakehouse 的开源项目，强调 ACID、可扩展元数据处理以及批流统一；Iceberg 官方把 schema evolution、hidden partitioning、partition evolution 和 time travel 明确列为核心能力；Hudi 则把 timeline 定义为表状态变化的事实来源。也就是说，湖仓一体的关键从来不是“湖上跑 SQL”，而是**表格式、元数据、快照、事务、演进与多引擎共享**。

这一节最重要的面试结论，可以归纳成一句话：  
“**Hadoop 解决大规模分布式底座，Hive 解决 SQL 化，Spark 解决统一计算与复用，Kafka + Flink 解决实时链路，Trino/ClickHouse/Doris 等解决低延迟分析，Iceberg/Hudi/Delta 解决湖上表语义。**”这句话如果能展开到“为什么、怎么做、适合谁、不适合谁”，基本就达到了高级数据研发或中级以上面试的结构化要求。

> [!quote] 面试一句话
> 平台组件要按职责记：存储底座、加工引擎、实时链路、查询服务、共享表层、治理能力，混在一起就容易选型失焦。

## 数据平台工程化与 AI 数据工程

> 数据平台工程化、大数据与 AI 数据工程，以及从 BI 数据链路扩展到特征、向量、RAG 和 Agent 数据服务的路径。

> 本节配图为“从 BI 到 AI 的数据工程链路图”：左侧是业务库、日志、文档、事件流，中间展示清洗切分、湖仓沉淀、特征工程、向量检索等处理带，右侧落到 BI、Feature Store、Vector DB、RAG 与 Agent。图注：**AI 数据工程不是替代大数据平台，而是把数据平台延展到特征、向量和检索增强生成。**

![[assets/bigdata-evolution/05-ai-data-engineering.png]]

> [!summary] 本节速读
> - 平台化的核心是把调度、元数据、血缘、质量、安全、资源和成本做成可运营能力。
> - AI 数据工程不是替代大数据平台，而是在原有底座上增加特征、向量、检索和反馈闭环。
> - 数据研发的升级方向，是从“出表”走向“出指标、出特征、出检索能力、出可复现数据资产”。

### 平台化瓶颈

很多团队的瓶颈，到了中后期已经不再是“有没有 Spark/Flink/Kafka”，而是“**这些能力有没有被平台化**”。调度系统要解决任务编排、依赖、回填、优先级和时效；Airflow 文档现在把“dataset-aware scheduling”正式引入调度语义，也就是上游数据更新可以直接驱动下游 DAG；Deadline Alerts 则把“任务是否超时”从人肉看板变成平台能力。换句话说，现代调度系统已经不只是 cron 的高级版，而是在往“数据驱动调度 + SLA 监控”方向演化。

### 元数据、血缘与质量

元数据、血缘和数据质量，是平台从“可用”走向“可运营”的三件套。OpenLineage 把 lineage metadata collection 做成开放标准，围绕 dataset、job、run 三类核心实体扩展；Airflow 的 OpenLineage provider 能额外上报输入/输出数据集和部分列级血缘；DataHub 则把 discovery、metadata、lineage、profile、governance、data contracts 集成到现代数据目录中；Great Expectations 强调 expectation、validation 与 orchestrator 集成，把数据质量从“事后查错”改成“进入生产前拦截与告警”。这些能力叠加之后，数据平台才能真正回答“这张表从哪来、被谁用、坏了会影响谁、什么时候修复完”。

### 安全、资源与成本

权限、安全、资源治理和成本治理，本质上是同一类问题的不同面：**平台如何把共享资源变成可控资源**。在批式时代，这体现在队列、资源池、任务优先级、存储生命周期和大表扫描控制；在实时时代，则体现在 topic 规划、状态大小、反压、Checkpoint 频率、OLAP 副本数与冷热分层；在湖仓时代，还要加上对象存储请求成本、元数据膨胀、manifest 数量控制以及 compaction/merge 策略。很多面试中所谓“数据治理做了什么”，真正想听的不是口号，而是你是否能说出**具体治理抓手**。

### AI 数据工程

进入 AI 时代后，数据工程的目标进一步变化。传统 BI 链路追求的是“统计结果一致”，而 AI 数据工程追求的是“**训练、检索、推理三条链路的数据一致且可复现**”。Feature Store 的官方定位很明显：原始数据先被转成 feature，再服务于探索、训练与推理；Amazon SageMaker 文档就把“create, store, share, manage features”作为 Feature Store 的核心价值。向量数据库则把 embedding 索引与相似检索工程化，Pinecone 官方强调“写入后可快速检索、索引自动化、查询低延迟可扩展”。而 RAG 管道里，LangChain 文档将 retrieval 到 RAG 的逻辑说得很清楚：检索在运行时提供上下文，RAG 则把检索和生成组合起来，输出有依据的答案。

这意味着 AI 数据工程不是“再加一个向量库”这么简单，而是至少包含七个步骤：**采集、切分、清洗、抽取结构化元信息、生成 embedding、建立索引、在线反馈回流**。如果你有实时需求，还要把 Flink/Kafka 这类流处理能力接进来，做实时特征或近实时文档索引；如果你有训练与 serving 一致性要求，还要让 Feature Store 和 Lakehouse 成为同一元数据体系的一部分。Iceberg/Delta/Hudi 这类表格式，以及现代元数据平台，正好为这种“批、流、特征、向量共用底座”提供了可能。

从职业演进看，数据研发要向 AI 数据工程师升级，最需要补的不是“再学一个框架”，而是四个能力：  
**第一，数据资产化能力**：把表、特征、文档、embedding 都纳入 catalog 与血缘；  
**第二，在线化能力**：理解数据什么时候进入实时链路，什么时候进入检索链路；  
**第三，服务化能力**：不仅输出表，还输出 feature service、vector index、RAG dataset；  
**第四，评估闭环能力**：知道离线指标、在线命中率、召回质量、延迟、成本怎么联动。  
这部分并非某一个单一官方文档直接给出的“标准答案”，而是基于 Feature Store、Vector DB、RAG 文档与 Lakehouse 官方能力做出的工程综合。

### 能力地图

下面这张“数据平台能力地图”，适合直接拿去做培训或项目汇报：

| 能力域 | 关键能力                     | 对数据研发的落地动作            |
| --- | ------------------------ | --------------------- |
| 调度  | 依赖、回填、SLA、事件驱动调度         | 规范 DAG、回填策略、超时告警      |

| 质量  | Expectation、校验、异常检测、数据契约 | 空值率、重复率、波动率、口径校验      |
| 安全  | 权限、脱敏、PII 审计、访问控制        | 表级列级控制、敏感字段标识         |

| 服务层 | 指标服务、标签服务、特征服务、向量检索      | 从“出表”升级为“出能力”         |

表中平台能力的事实依据来自 Airflow、OpenLineage、DataHub、Great Expectations、Feature Store 与 Vector DB 官方资料；“落地动作”部分是工程化归纳。

> [!quote] 面试一句话
> 数据平台工程化的价值，是把一次性脚本能力沉淀成可发现、可追踪、可校验、可授权、可控成本的长期资产。

## 技术选型与工程实践方法论

> [!info] 本节覆盖

### 选型误区

技术选型最常见的误区，是拿一个系统去解决它并不想解决的问题。比如用 Hive 做秒级交互式分析，用 ClickHouse 承担复杂长链路 ETL，用 Flink 去做重型离线宽表回刷，用 Kafka 充当长期历史归档，用 Trino 承担高并发实时明细聚合服务——这些都不是“能不能跑”的问题，而是**设计目标不一致**的问题。官方文档通常已经给出了每个系统的目标边界：HDFS/MapReduce 面向大规模批式底座，Spark 是统一分析引擎，Flink 面向流式执行与状态一致性，Trino 面向并行分布式查询，ClickHouse/Doris/StarRocks 面向低延迟分析，Iceberg/Hudi/Delta 面向 Lakehouse 表语义。

### 选型四问

如果进一步落到项目决策，可以按这套“选型四问”来判断：  
**第一问：延迟目标是什么？** T+1、分钟级、秒级、亚秒级分别会把你推向 Hive/Spark、Kafka+Flink、MPP OLAP 的不同组合。  
**第二问：数据形态是什么？** 是 append-only、CDC、无界事件流，还是多源联邦查询。  
**第三问：一致性要求是什么？** 允许最终一致、至少一次、还是要求端到端 exactly-once。  
**第四问：服务模式是什么？** 是“给工程师跑任务”，还是“给分析师查 SQL”，还是“给业务方提供在线指标/特征/检索服务”。这四问答出来，很多技术争论会立刻消失。

### 工程建议

一个特别实用的工程建议是：**把“数据加工”和“数据服务”两件事分开设计。**  
用 Spark/Hive/Flink 负责数据加工；  
用 Kafka 负责链路解耦；  
用 Trino/ClickHouse/Doris/StarRocks 负责查询服务；  
用 Iceberg/Hudi/Delta 负责共享表层；  
用元数据/血缘/质量系统负责治理。  
很多团队之所以越来越复杂，不是组件太多，而是拿一个组件同时承担了“加工 + 服务 + 治理”的三种角色。

> [!quote] 面试一句话
> 好选型不是追最新组件，而是让延迟、数据形态、一致性、服务对象和运维成本同时闭合。

| 面试路线 | HDFS/Hive/Spark → Kafka/Flink → ClickHouse/Doris → 湖仓 → 平台治理 | 以面试频率最高的原理题和项目题为主，不求组件全，会求逻辑强 | 复盘一离线一实时两类项目，各写一页架构说明和调优清单 | 能结构化回答九类高频题，能把项目讲出“背景—挑战—方案—结果—复盘” | 我能说 Spark 为什么快；我能解释 Watermark；我能对比 Hive、Trino、ClickHouse；我能说一个治理案例 |
| 高阶架构路线 | 分布式存储与计算原理 → 多引擎架构 → 平台治理 → 湖仓 → Feature/Vector/RAG 数据工程 | 从“会用”升级到“会设计、会治理、会权衡” | 设计统一数据平台方案：批流一体、OLAP、湖仓、数据目录、质量、特征、向量检索 | 能从问题出发做选型，能解释技术边界，能做架构 trade-off | 我能画出数据平台能力图；我能解释为什么上湖仓；我能说明 AI 数据工程如何复用现有大数据底座 |

这些学习路线是对前文技术体系和工程环节的综合组织，不对应单一来源。

### 术语索引

下面附上**术语索引**，建议你当成考前速记表。

| 术语 | 一句话解释 |
|---|---|
| NameNode | HDFS 元数据主节点，维护命名空间与 block 映射 |
| DataNode | HDFS 数据节点，负责 block 存储与读写 |
| Block | HDFS 的文件切块单位 |
| Replication | HDFS 副本因子，用于容错 |
| FsImage | HDFS 命名空间快照文件 |
| EditLog | HDFS 元数据变更日志 |
| Shuffle | 按分区规则重分布数据的过程 |
| RDD | Spark 的弹性分布式数据集，靠 lineage 容错 |
| DataFrame | Spark 结构化数据抽象，更利于优化器做事 |
| Dataset | JVM 世界里兼顾类型安全与优化器收益的抽象 |
| DAG | 有向无环图，表示任务依赖与执行计划 |
| Stage | 被 shuffle 边界切开的执行阶段 |
| Task | 一个分区上的最小执行单元 |
| AQE | 自适应查询执行，依据运行时统计调整计划 |
| Watermark | 事件时间进度信号，表示系统大致不再期待更早事件 |
| Window | 对无界流按时间或计数切片计算的机制 |
| State Backend | Flink 状态存储后端 |
| Checkpoint | Flink 一致性快照，用于故障恢复 |
| Savepoint | 手动触发的 Flink 程序快照 |
| Exactly-once | 在失败恢复后仍保证语义上只处理一次 |
| Topic | Kafka 的逻辑主题 |
| Partition | Kafka 的并行与顺序基本单元 |
| Offset | Kafka 中消息在分区内的位置 |
| Consumer Group | Kafka 消费并行与负载均衡单位 |
| MPP | 大规模并行处理架构 |
| Vectorized Execution | 按批处理数据而非逐行处理，提高 CPU 利用率 |
| Predicate Pushdown | 把过滤尽量下推到更靠近数据的地方 |
| Column Pruning | 只读取查询需要的列 |
| Partition Pruning | 只扫描命中的分区 |
| Metastore | Hive 等系统中的表元数据服务 |
| Snapshot | 湖仓表在某一时刻的一致性视图 |
| Manifest | Lakehouse 表格式中描述数据文件集合的元数据 |
| Timeline | Hudi 中记录表状态变化的动作日志 |
| Time Travel | 在旧快照上阅读数据的能力 |
| Schema Evolution | 表结构随时间演进而不破坏读取 |
| Feature Store | 特征的生产、管理、共享与服务系统 |
| Vector Database | 为 embedding 检索而优化的索引与查询系统 |
| RAG | 检索增强生成，把检索上下文喂给 LLM 再生成答案 |

术语解释与前文保持一致，其中涉及特定系统定义的部分可回看对应官方资料。

## 开放问题与说明

本文侧重体系化、工程化与面试表达，没有逐条展开所有产品 API 级细节，例如 Delta Lake/Hudi 的特定命令级 time travel 用法、Presto 某些社区分支演进，以及少数非核心生态组件。面试题部分按模块给出高频问题与回答锚点，并为最高频问题提供完整模板；如果把每个模块的问题都展开成长答案，反而会削弱主线阅读效率。

这份报告最应该带走的，不是某个参数、命令或组件名，而是一条主线：**从核心矛盾理解技术，从系统原理理解平台，从工程边界理解选型，从结构化表达把知识转化为面试能力。**只要你按这条主线复习，Hive、Spark、Flink、Kafka、ClickHouse、Lakehouse、平台治理与 AI 数据工程就不再是零散知识点，而会变成同一张大图里的不同层。
